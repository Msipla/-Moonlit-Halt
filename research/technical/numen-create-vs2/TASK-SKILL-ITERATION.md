## 二、问题与目标

上一阶段三组空场粉碎机建造均失败：A 大面积铺地，B 机械没有动力，C 水车 ±8 RPM 但粉碎轮 0 RPM 且无控制器；已授权 B 组能修复错轴并真实产沙，却额外加了大量水。说明模型会用 Numen 工具，但未能稳定将现有 Skill 知识转化为分阶段施工与独立验收。

**首要目标：** 验证只改进现有 Create Skill 的规则和反馈使用顺序，是否足以显著改善从零自主建造与故障诊断；优先让 DeepSeek 在真实 Minecraft 世界中建成、驱动、投料并验收一台粉碎机。允许失败，禁止用预写固定施工/修复脚本冒充自主成功。

## 三、实施阶段

### 阶段 1：定位可纠正的行为

基于已有失败记录，提炼不超过 3—5 条可检验规则，优先覆盖：

- 不做与当前目标无关的大面积整地、铺底、填水；先最小结构，再验证，再扩展。
- **动力源检查**：放置水车后读取实际 RPM；有水不等于有有效流动。
- **传动链检查**：水车有 RPM 但末端粉碎轮 0 RPM 时，沿对应支路逐段核对传动轴轴向、接触和网络，不要直接判定缺水。
- **控制器检查**：确认两侧粉碎轮有效转速/方向、间隙无错误方块、控制器有效，再进入投料。
- **产物与清理**：以实际碎石→沙子、容器读数和多余施工块检查作为完成标准，不以方块放置回执或模型自述替代。

不要把上次正确答案坐标、固定完整蓝图或预写 Lua 塞入 Skill；Skill 应是通用工程规则而非死记一台夹具。

### 阶段 2：最小 Skill 改动与公平对照

1. 保留旧 Skill 内容作为 Git 基线，不改上阶段日志；只对现有 `create_kinetics/SKILL.md` 做必要的小范围修订，避免新建平行 Skill 或知识库。
2. 用相同的 DeepSeek 模型、相同中文目标、同种子/区域/权限/材料/工具与相同时间及调用上限，比较 **旧 Skill + 既有只读探针** 与 **新 Skill + 同一只读探针**。至少各做一次完整实测；若资源允许增加重复样本，报告样本数与随机性，避免一次成败被过度解释。旧版应从 Git 历史或基线文件临时载入，不在仓库新增重复正式 Skill。
3. 保持原有 Numen 自主工具调用，模型自行规划/生成 Lua/选择方块。夹具仅负责统一环境、观察、投料、注障和独立验收，不提前执行目标施工。可用已归档的真实机器副本补测错轴修复。
4. 对比模型实际调用 Skill 和状态探针的频率、读取反馈后采取的行动、建造是否成功、故障修复是否成功、净方块变更、无关施工/越界、水扩散、用时、token 和估算费用。
5. 采用实际 Minecraft 运行状态：水车与两侧粉碎轮有效 RPM、应力/容量、控制器有效性、真实碎石输入和沙子输出；失败时报告停在哪一关。

### 阶段 3：施工边界（只在必要时做最小补丁）

上一阶段模型经 OP 的 `numen.mc.run` 使用 `fill`、`setblock`，造成大量无关改动；Skill 文字本身不能保证硬性限制。先评估现有权限、命令白名单、施工区域和测试夹具能否约束；**优先在现有执行侧/夹具复用或添加最小的范围、单次改动量和危险命令限制**，不要开发新权限框架，不修改 Numen 核心。若无法在不改变对照条件下限制，先完整记录并独立进行约束实验，不把限制变化和 Skill 变化混为一谈。

若新 Skill 仍失败，结合日志判断是规则不清、模型规划、工具反馈不足、权限或模型上下文限制；只有存在明确缺失且可证明必要时，才允许小幅修复现有探针/测试脚本。不要直接扩展 VS2、Eureka、Clockwork、航空学或移动基地适配。
