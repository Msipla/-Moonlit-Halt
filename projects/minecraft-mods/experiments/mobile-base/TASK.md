## 核心产品原则（用户已确认，优先级最高）
1. **代码层面实现「非法组装」**：玩家可以用任意普通方块建造奇形怪状的载具，不必满足其他 Mod 原生的机械装配前置条件。通过适配/替代组装流程，使其最终成为**底层有效的 VS2 等真实物理载具**。可以绕过玩法限制，不能跳过必需的数据初始化、碰撞安全和存档完整性检查；失败不得伪报成功。
2. **按载具类型自动补全必要装置**：陆地房车、轮船、飞行器、潜艇分别配置其真正需要的车轮/转向、推进/浮力、飞行、潜航等功能。优先复用现有成熟 Mod 的实际组件、接口和参数；必要时编写最少的适配代码。**不要求机械结构隐藏**，可见零件正常显示即可；也不强制使用某一种复杂传动链。
3. **安装位置可选，有合理默认值**：玩家用简单标记工具右键已有方块表面，按需标记车轮、驾驶位、朝向及其他确有必要的部件位置。未自定义的由系统选择可用默认位置。若需要调整布局，使用最简洁的半透明预览与确认即可；不要开发复杂蓝图编辑器。自动放置必须避免破坏内饰、容器及玩家原有建筑；冲突时提示调整，不得静默覆盖。
4. **组装后适配到「能开动」**：不能出现虽然强制组装成功，却因缺少传动、动力不足、浮力不足、过重或外形不合理而根本无法使用的载具。优先采用**最容易实现且稳定**的现有组件参数调整、动力/浮力补足或最小控制适配，让当前载具正常前进、转向、停止，并保留合理的质量、重力、惯性、碰撞与载具内部活动。优先针对单个载具配置，避免修改全局物理参数影响其他载具。**不要求复杂的重量感模拟、统一手感或专门的辅助驾驶系统**。
5. **不做没必要的功能**：能用现有机制解决就不造新系统，能少改就少改。保护已验证的游轮/房车能力；不为形式完整提前实现四种类型的空壳，不引入 AI API、自然语言建造、自动寻路、复杂预制件系统、重写 VS2 物理引擎或无关美术翻新。

**验收例子：黄金船。** 玩家用大量黄金块造出不符合现实造船规则的奇形怪状船体，只需选择船型、必要时标记驾驶位/方向，系统自动补足必要机械或配置，绕过不必要的原生组装限制，完成有效物理组装，并以最简单可靠的方式补足浮力和推进能力，使其不会因过重而注定沉底、可以正常航行。保留碰撞和物理效果。此例用于验证产品方向，不意味着必须模拟真实流体或采用特定公式。

## 工作顺序（在授权范围内自主推进）
**A. 恢复与最小方案选择。** 直接以现有已验证原型为基础，不重复审查既往视频和测试；只检查实现新增功能所必需的接口与风险。列出「原生装配限制」「缺失部件」「物理参数导致不可驾驶」各自的最小处理路径。比较最简单的可用方案，不为追求技术纯粹性引入额外系统。

**B. 先打通一种完整的「非法组装→补全→能开动」闭环。** 优先在已验证的船或房车上增量实现，选择代码改动和验证成本最低的一种；说明选择依据。实现标记/默认位置、必要部件补全、真实物理装配、动力/浮力适配、驾驶/停车。已有功能可直接复用，避免重复开发。

**C. 扩展并验证。** 在第一种闭环可靠后，按依赖成熟度和实现成本扩展到其余载具类型：陆地、船、飞行器、潜艇。目标是四种类型都支持上述统一体验；允许分阶段交付，但不得将仅有选择按钮或空壳标为已实现。遇到明显技术阻塞，提供源码证据、最小替代方案及代价，涉及重大架构变化先请示。

**D. 保护移动基地核心体验。** 保留/验证行驶中离开驾驶位、在内部走动、使用储物容器、停车、解除组装、修改后重组装。尤其关注移动时转向、碰撞、方块实体/库存保留、解除组装的空间与坐标安全。禁止通过不安全传送、静默删除方块或覆盖玩家存档来制造「测试成功」。

## 执行边界与验收
- 仅在本项目必要范围内修改，禁止顺带重构 `ai-engineer`、《微光深渊》及其他稳定项目。保留可运行旧版，必要时使用隔离分支和测试世界。
- 先创造模式验证；生存模式完整材料消耗、多人联机、复杂预制组件、外观精装修、AI 建造、自动导航均不属于本轮必做。
- 对「组装成功」和「能正常开动」分别验证。至少展示一种**非标准/超重结构**实际完成装配、动力运行、转向、停止；对于船类还需验证不会因浮力不足立即沉底。不能只用标准船/标准车的既有视频替代新增功能测试。
- 尽可能在真实 Minecraft 环境实测，提供可核对的截图/视频或日志；测试行驶中离座、内部移动、储物交互、解除及重组装。无法实测须明确列出未测项，不得把编译/单元测试称为游戏实测。
- 提交必要源码、可复现依赖和构建说明、成功构建的 JAR（如有）、测试结果、已知限制、提交 SHA。准确区分「已编码」「已编译」「已实机测试」「用户已验收」。
- 完成阶段后检查任务书状态与必要交接，回读 GitHub 提交；优先维护现有文件，不创建重复任务书/报告。若关键能力不可行，说明原因与最小可行替代，不得擅自改掉用户确认的五条原则。

## 房车实机可行性验证（2026-11-19）

- 使用单独的 Minecraft Java 1.20.1 测试实例，Fabric Loader 0.17.2、Fabric API 0.92.6、[Valkyrien Skies 2.4.11](https://modrinth.com/mod/valkyrien-skies/version/qJr3y5vI)、[Eureka 1.6.4](https://modrinth.com/mod/eureka/version/Vim9JR4p)、[Create Fabric 6.0.8.1](https://modrinth.com/mod/create-fabric/version/HAqwA6X1)和 [Trackwork Refabricated 1.2.2](https://modrinth.com/mod/trackwork-refabricated/version/Mh7IDZZC)。7×17 房车装配 426 格，舱内有独立驾驶区、客厅、厨房、卧室和储物。Eureka 原生船舵执行组装。四轮悬挂采用 Trackwork，传动采用 Create 创造马达、齿轮箱、反向齿轮和离合器。驾驶操作由车内拉杆和转向按钮完成。
- 成品房车在专用服实测直行、左转、右转及平路停车。依次按下车内左、右转向按钮，横向速度分别约为 −0.67 和 +0.61 格/秒。设定 30 RPM 时，稳定直行约 2.44 格/秒。完整录像从静止启动后约 14 格离席，徒步经过客厅、厨房与卧室，从木桶取出书并由服务端确认进入物品栏，回到驾驶座断开离合。离席到停稳约 71 格。最后两次速度采样低于 0.001 格/秒，全程玩家飞行状态关闭。用户侧实录文件为 `Minecraft-living-RV-tour.mp4`。
- 一次在已入座时用测试指令复位车体，随后离席回到旧位置。成片在上车前完成复位。录像内的行驶、离席、步行、储物与停车均通过原生游戏操作完成。坡道驻车、转弯时舱内走动以及长时多人兼容性待验。陆地自动装配核心、选位补件和解体回收待后续产品化。
- 预制组件先评估 [Create 原生滑门](https://create.fandom.com/wiki/Sliding_Door)和[现有 NBT 蓝图](https://github.com/Creators-of-Create/Create/wiki/create-schematics)。独立车厢或拖挂可参考 [VMod 约束](https://valkyrienskies.org/addons/vmod)，需要先验证断开、重载和碰撞。此轮为资料调查。

## 2026-11-19 第一阶段交付

- 先做船型，沿用 VS2 和 Eureka 已有的搬运、燃料、浮力、红石锚与巡航。房车实测使用另一套 VS2、Eureka、Create 与 Trackwork 版本。陆地自动装配需验证轮组、动力和转向自动补全后再决定如何兼容，飞行器和潜艇按后续阶段推进。
- 取消水面船原型的 80,000 千克装配限制，按单船水线、浮力块和实际质量适配浮力及真实燃料引擎输出。标记棒可指定船舵、引擎、浮力块与船头方向，预览和确认保留安全检查。
- 创造模式专用服实测异型黄金船。144 格船体补齐 9 个部件，质量约 2,012,940 千克。标记冲突时原方块和库存保留。首艘船可转向、离席巡航、开木桶和抛锚停稳。
- 最终构建验证了原生船舵对齐、核心解体和改装重组。原生锚令物理船静止时，核心用相邻帧位姿验证静止，继续检查朝向、落点和船上实体。153 格还原，手动添置橙色玻璃后重组为 154 格，已有部件与木桶库存保留。
- [可安装 JAR](artifacts/mobile-base-assembler-0.2.0-alpha.1.jar) · [实机采样与存档核对](evidence/gold-boat-0.2.0.json) · 实录文件 `Minecraft-heavy-gold-boat-demo.mp4`。录像覆盖选位、首装、航行和抛锚。最终包补加解体时的静止核验，解体和重组在同一船续测。
- 新版待用户验收。独立装配以创造模式和深水为测试范围。新版的高速度撞岸、极窄船体、多人并发和长期稳定性仍待实测。
